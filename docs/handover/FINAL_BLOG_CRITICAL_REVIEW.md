# 博客项目最终批判性审查与建设性验收

审查日期：2026-08-29  
审查对象：正式 Astro 源码、构建产物、内容资产、ArcVellum 外部工程、求解器 C/Wasm、本地 Blog Studio 与运维文档。  
判断口径：这是一个个人博客和长期内容系统，不是功能演示集合，也不是 SaaS 产品。

## 总评

项目已从“视觉原型加若干文章”跨过了博客工程的基本完成线：内容可维护、路由可证明、媒体有契约、搜索和分发存在、文章与主题能逐级获得页面自由、复杂项目可以嵌入真实运行模块。它现在最有辨识度的不是粒子或星图，而是“文章 / 主题 / 独立项目文档站 / 本地维护工作台”四层自由度可以共存。

综合评价：**可作为个人长期博客上线，仍不应被宣称为成熟 CMS 或完整 ArcVellum Web 客户端。**

## 一、架构思想

### 成立的部分

1. **静态页面是主体，交互是可拔插增强。** 普通文章关闭 JavaScript 仍可读，搜索、评论、统计和复杂实验不反向绑架内容。这比将整站做成客户端应用更符合个人博客的寿命预期。
2. **构建时分派解决了 Astro 样式聚合的实际问题。** `full / minimal / none` 不是一个运行时条件组件，而是六个隔离入口；`none` 因而能真正不注入全站外壳。这是工程决定，不是 frontmatter 装饰。
3. **内容与真实媒体共置。** 封面进入 Astro 图像元数据管线，避免再次发生把 `/cover.png` 字符串传入图像组件导致的运行错误。默认封面仅兜底，不冒充项目实拍。
4. **高自由度内容没有污染全站。** ArcVellum、实验主题和求解器各自持有组件与样式；标准文章仍使用稳定排版。
5. **学习笔记退出主题集合。** 它现在有独立 schema、路由、公开状态、同步清单和附件规则，语义上终于是知识模块，而不是一个空壳分类。

### 仍需警惕

1. `columns` 是内部历史名，公开语义已改为“主题”。保留它避免 URL 与内容迁移是合理的，但新开发者必须阅读约定，否则会重复引入“栏目 / 主题”双语义。
2. `src/components/arcvellum/docs.ts` 仍是手工文章清单。ArcVellum 文章继续增加后，建议把层级、序号和分组迁入 frontmatter，由集合查询生成侧栏，避免“有文章但忘记进目录”。
3. 三档 chrome 带来真实自由，也带来六入口测试矩阵。新增第四档之前应先证明它不能由现有档位加局部组件表达。
4. Blog Studio 与站点共享文件系统，但不是事务型 CMS。并发打开两个编辑窗口、外部编辑器同时保存、批量重命名等场景尚无冲突合并。

## 二、可扩展性

### 内容扩展

- 新主题可以拥有自己的 Astro 页面、媒体、脚本和文章集合；普通主题不必复制 ArcVellum 的自由度。
- 文章封面统一为 16:9 显示契约，主题卡、首页 hero、列表和正文只改变尺寸，不改变裁切语义。
- 正文媒体不受封面比例约束；宽图、出血图、竖图、左右浮动均按固有比例回流。
- ArcVellum 已按产品、文学内核、Agent / 工作流、空间前端、工程发布五层建立 50+ 项编辑清单；当前十二篇文章只是已发布子集。

### 功能扩展

- Solver 展示器证明复杂本地工程可以通过 Wasm/Worker 嵌入文章，而不是以截图或外链代替。
- ArcVellum Demo 证明某个主题可以拥有独立视觉语言，同时继续遵守站点的路由、回退和静态产物契约。
- Notes 同步器把本地 Vault 映射为公开只读集合；后续可以加入增量哈希、删除策略和冲突报告，但不应默认双向写回用户源目录。
- Blog Studio 的命令白名单、路径白名单和回环绑定为后续扩展保留了安全边界。增加部署按钮前，必须继续让令牌停留在服务端进程，不进入浏览器状态。

## 三、视觉批判

### 已解决的根本问题

1. **桌面不再像窄版文档。** 全局内容上限扩为 96rem，主 hero 与首页模块有足够体量；重点封面能够被看清。
2. **首页主次与内容战略一致。** 主题在左侧占大空间，继续阅读在右侧只显示三篇；两者卡片规格不同，避免对称模板感。学习笔记作为独立大模块插入信息流，而不是再增加一排旧链接。
3. **封面完整优先。** `contain` 与 16:9 稳定画布使项目截图、计算图和长宽不一的真实图不会被裁掉核心区域；背景色和纹理吸收留白。
4. **配色有规则而非轮播。** 页面只保留 mist / abyss；钴蓝、柿红、鸢紫、赭金是内容身份强调色，不按列表位置循环。大面积基底保持低饱和，小面积信号负责节奏。
5. **动效有功能归属。** 开场动画、页边粒子、首页 hero 指针扰动和 ArcVellum 天穹分别承担品牌入场、环境注释、重点文章响应、空间模型解释，不再是同一种粒子换色复用。

### 仍不够好的部分

1. **首页仍偏“展览目录”，生活气息不足。** 目前的信息密度来自项目、状态和指标，适合技术型作者；若博客未来加入随笔、摄影或日常记录，需要更松弛的日期、地点、短注或单图节奏，否则每个区块都像产品说明。
2. **真实截图的风格差异被完整保留，也暴露了素材质量差异。** `contain` 解决裁切，却无法让低分辨率、密集 IDE 截图自动变成好封面。后续每篇重点文章应人工选取视觉焦点，必要时制作“截图 + 局部放大 + 简短标注”的编辑封面。
3. **大号标题与等宽微文案使用频率偏高。** 它们建立了独特性，但在 ArcVellum、求解器和首页连续出现时会产生展陈疲劳。新增普通文章不应继续复制全大写 eyebrow + 巨题 + 指标四格。
4. **ArcVellum Demo 的空间感已真实成立，但仍是缩编。** 它使用 Pixi/WebGL、章节星核、黄金角场景簇、四元数轨道、正式投影比例、深度缩放和 DOM 命中层；没有引入完整 `pixi-viewport`、后端 Projection v4、窗口系统、SkyMesh shader 或动作端口。它和实际工程“同技术路线、相近观感”，不是相同应用。
5. **移动端只能回流，不能保留全部桌面错落。** 这是正确取舍。若强行在 390px 保留左右错位，只会损害可读性；移动端的设计价值应放在顺序、触控和首屏节制上。

## 四、工程完备性

### 已验证

- 内容审计：24 篇文章、6 个主题、1 个公开笔记集合。
- 媒体审计：28 张真实封面、2 张确定性默认封面；真实资产进入图像优化管线。
- 静态构建：99 个页面，Pagefind 索引 27 个正文页面、3892 个词。
- 链接：99 个 HTML 文件内部链接全部通过。
- 体积：gzip JavaScript 157 KiB，CSS 148 KiB，均在当前预算内。
- Astro：96 个文件，0 error / 0 warning / 0 hint。
- Solver 快速冒烟：识别 33 步、10 次转向，约 0.9 秒。
- Solver 完整冒烟：规划 191 步、86 次转向，重复运行约 34.4–43.6 秒；浏览器上限已留到 60 秒。
- Notes dry-run：能识别公开状态并生成稳定目标路径。
- Blog Studio：回环地址、一次性 token、未授权 401、文件树和读取 API 已验证。

### 部署前仍缺外部证据

1. 真实 `SITE_URL`、域名、DNS 与托管账号尚未配置；因此 canonical 在未配置环境仍会使用示例值。
2. 评论和统计默认关闭；启用需要站主选择 provider，并在隐私页披露真实数据流。
3. 尚未取得一次公网部署后的 Core Web Vitals、分享卡抓取、RSS 订阅器和 404 回退证据。
4. Solver 完整模式受机器性能影响明显。当前机器约 34.4–43.6 秒，在低性能移动设备上仍可能超过 60 秒；上线后应把“完整规划耗时较长”写在按钮附近，并考虑按地图复杂度分级。
5. 本地 Studio 不应直接公网暴露。若将来远程使用，需要真正的身份认证、CSRF 防护、审计日志和冲突模型，不能只把绑定地址改为 `0.0.0.0`。

## 五、外部标准对照

- W3C WCAG Reflow：普通内容在等效 320 CSS px 宽度下不应要求页面级双向滚动。复杂 Canvas 可以局部例外，但页面本身仍应回流。  
  https://www.w3.org/WAI/WCAG21/Understanding/reflow.html
- web.dev Responsive Images：`cover` 会裁切，`contain` 保留完整图像；博客中的项目截图属于应优先保持完整性的内容图，而不是装饰背景。  
  https://web.dev/learn/design/responsive-images
- web.dev CLS：图片固有尺寸或 `aspect-ratio` 应预留空间；本项目统一封面画幅和 Astro 元数据可降低加载位移。  
  https://web.dev/articles/optimize-cls
- Astro 本地图片规则：本地资产必须被导入或通过内容 schema 的 `image()` 解析，不能把字符串路径直接传给图片优化器。  
  https://docs.astro.build/en/reference/errors/local-image-used-wrongly/
- VS Code Workbench：Activity Bar、Side Bar、Editor、Panel、Status Bar 是 Blog Studio 的信息架构参照；界面没有复制 VS Code 皮肤。  
  https://code.visualstudio.com/api/extension-capabilities/extending-workbench
- File System Access API 需要显式授权且浏览器支持不一致，所以稳定方案仍是回环 Node 服务；目录选择 API 只适合作为增强。  
  https://developer.mozilla.org/en-US/docs/Web/API/File_System_API

## 六、建设性路线

### 上线前必须完成

1. 配置真实 `SITE_URL`，运行 `pnpm deploy:check`、`pnpm verify` 和浏览器 E2E。
2. 在真实托管预览中检查 390×844、1366×768、1440×900、1920×1080 四个视口。
3. 用真实分享抓取器、RSS 阅读器和无痕浏览器验收一次。
4. 为评论、统计与第三方字体作最终启用/禁用决定，并同步隐私说明。

### 上线后优先

1. 以三篇访问量最高文章为样本人工重做封面，而不是继续批量生成风格相似的抽象图。
2. 将 ArcVellum 文档侧栏从手工清单迁移到 frontmatter 分组，逐批完成 P0/P1 文章。
3. 为 Notes 加增量哈希、孤儿附件报告和明确的删除策略。
4. 用真实访问数据观察首页是否需要“短记 / 最近在做 / 一张图”模块；没有证据前不再增加仪表盘卡片。

### 明确不做

- 不恢复阅读编排器或站内链接工作台。
- 不把学习笔记重新包装成主题。
- 不增加第三种站点色彩主题。
- 不用重型客户端框架重写标准博客页面。
- 不把模拟 ArcVellum 数据描述为真实项目连接。

## 最终结论

这个博客已经具有可识别的作者性：克制的双主题、内容身份色、完整项目封面、文章级自由、真实可运行工具和独立的文学工程空间。它也具备工程上的诚实：模拟数据被标出，Wasm 有真实路径，未来文章列为 backlog，本地维护台不冒充云 CMS。

下一阶段最重要的不是再增加功能，而是上线取得真实使用证据，然后通过少量高质量封面、持续写作和 ArcVellum 分层文章，把已有架构转化为内容资产。
