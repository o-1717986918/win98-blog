# 沉浸式空间博客：可行性与实验架构

> 状态：概念论证，尚未进入生产主线  
> 日期：2026-08-28  
> 前置约束：以 `docs/source/blog-architecture.md` 为唯一架构依据

## 1. 结论

可以做，而且有机会形成真正有辨识度的个人博客入口；但不应把“整个博客都画进 Pixi”理解为把正文、链接和表单全部变成纹理。更稳健的实现是一个**空间场景层 + 语义文档层**的双层系统：

- Pixi/WebGL 负责粒子环境、空间导航、栏目方位、远景文章入口和镜头反馈；
- 真实 DOM 负责正文、链接、选区、代码、表单、搜索、SEO 和辅助技术；
- 两层共享同一份内容清单、URL 状态和主题 token，由镜头状态决定哪个 DOM 阅读平面进入前景；
- 普通静态博客始终是可靠底座，空间场景是渐进增强，不成为内容可访问性的单点故障。

因此，推荐先把它建设成 `/lab/spatial/` 下的可选实验入口，而不是直接替换当前首页。

## 2. 为什么不能只用 Pixi

Pixi 的 scene graph 很适合管理大量具有父子变换关系的二维对象；`PerspectiveMesh` 也能让二维平面呈现透视形变。这足以完成“空间中的栏目、文章门扉、粒子和远景层”。但 Pixi 仍以二维渲染为核心，它并不是完整的三维文档排版系统。

长文如果直接绘制为 Canvas/WebGL 纹理，会损失或显著增加以下能力的实现成本：

- 文本选择、复制、浏览器查找和原生链接；
- 屏幕阅读器的阅读顺序、键盘焦点和语义标题；
- 搜索引擎、RSS、打印样式与无脚本访问；
- MDX 组件、代码块、评论和复杂表单的维护性。

所以，“一切都是场景中的元素”应理解为**一切都拥有空间位置和镜头关系**，而不是“一切都必须由同一个 Canvas 绘制”。

## 3. 视觉母题：个人知识观测场

场景不是游戏大厅，也不是星图分类器，而是“win98的小站”的空间化目录：

- **中心锚点**：站点身份、最近更新和返回主页；保持简朴，不做巨大品牌雕塑。
- **栏目扇区**：栏目是开发者可自由添加的方向或区域，不承载文章自由度等级。
- **文章平面**：每篇文章是栏目区域中的薄片、门扉或光学面；不同 `chrome` 档只影响进入后的外壳，不决定它在空间中的类别。
- **远近关系**：时间、阅读关系或作者策展顺序可以影响距离和聚集，但不成为强制层级。
- **背景粒子**：提供尺度、速度与景深线索；不承担主导航，也不抢夺阅读焦点。

视觉上采用低饱和蓝与暖橙作为两个稳定光域，再用中性色和少量紫色过渡。色彩表示空间气氛，不把文章类别硬编码成颜色。

## 4. 交互模型

### 4.1 空间浏览

- 鼠标拖动或单指拖动：绕中心旋转视角；
- 滚轮、触控板或双指：推进/拉远；
- 悬停或键盘聚焦：文章平面轻微转向观察者并显示标题摘要；
- 点击或 Enter：镜头沿曲线移动到目标平面，URL 进入真实文章地址；
- Esc、返回键或浏览器后退：镜头退出阅读态并恢复上一个空间位置；
- 顶栏始终保留小型搜索框，搜索结果定位并高亮场景对象，而不是另开一套大型界面。

### 4.2 阅读态

镜头到达文章平面后，真实 DOM 阅读层由低清晰度空间卡片过渡为稳定的正面阅读平面。进入长文后应限制镜头漂移，避免“阅读时晕动”。用户仍可主动缩回空间视图。

### 4.3 导航保障

空间交互之外必须同时存在：

- 可聚焦的栏目/文章 DOM 导航树；
- 方向罗盘或微型平面图；
- “回到平面版博客”入口；
- `prefers-reduced-motion` 下的无镜头飞行动画；
- 移动设备上的列表式降级，而不是强迫用户精细拖拽。

## 5. 推荐技术架构

```text
Astro Content Collections / MDX
             │
             ├── 静态文章 HTML、RSS、sitemap、Pagefind
             │
             └── spatial-manifest.json
                       │
         ┌─────────────┴─────────────┐
         │                           │
  SpatialScene               SemanticDocumentLayer
  Pixi 粒子/入口/景深          DOM 正文/搜索/焦点/链接
         │                           │
         └────── CameraStore ────────┘
                 URL / History
```

### 场景层

- 第一阶段沿用 Pixi 8：scene graph、粒子容器、render layers、culling；
- 文章入口可用 `PerspectiveMesh` 做二维平面的透视与转向；
- 如果自由旋转和真实三维遮挡成为核心，则将镜头/几何升级为 Three.js 或 WebGPU，Pixi 保留为粒子和二维合成层；
- 不把框架组件树直接绑定到每帧 ticker，所有动画通过稳定的场景状态机驱动。

### 语义层

- 文章仍由 Astro/MDX 生成真实 HTML；
- 近景阅读平面使用 DOM，必要时用 CSS 3D 或矩阵同步到镜头；
- 页面 URL 仍为 `/posts/<slug>/`，刷新和无 JavaScript 时直接进入标准文章页；
- 空间模式可以通过 query、session 状态或 View Transition 恢复，但不能创造第二套内容身份。

### 状态边界

最小状态只包括：当前栏目、目标文章、镜头位置、空间模式开关和读者偏好。文章数据来自构建产物，不引入全站运行时状态管理。

## 6. 与既定博客架构的契约

1. **文章身份唯一**：空间入口、普通列表、RSS 和搜索都指向同一 URL。
2. **三档 chrome 不变**：空间场景只是入口；进入文章后仍由 `full | minimal | none` dispatcher 决定外壳。
3. **栏目保持自由模块**：空间位置来自栏目配置文件，开发者可以新增场景组件或完全定制某个栏目区域。
4. **静态优先**：首屏可由 Astro 输出完整的语义导航；场景加载失败不阻断阅读。
5. **加法设计**：空间场景作为可组合部件加入，而不是迫使 BaseLayout 或所有文章依赖它。
6. **正文不栅格化**：长文、代码、链接和交互组件继续由 DOM/MDX 承载。

## 7. 分阶段实验

### Phase 0 · 空间语法原型

只做栏目扇区、8—12 个文章入口、镜头旋转与键盘焦点，验证空间方位是否真的比列表更有价值。

### Phase 1 · 内容清单驱动

从 Content Collections 构建 `spatial-manifest.json`，禁止在场景代码里手写文章数据。加入视锥裁剪、低功耗模式和帧率预算。

### Phase 2 · 单篇 DOM 阅读平面

选择一篇 `full` 文章验证镜头靠近、DOM 接管、退出与浏览器历史。此阶段不做全站迁移。

### Phase 3 · 可访问性与输入系统

实现键盘路径、焦点回收、减弱动态、触屏手势、屏幕阅读器导航树和无 WebGL 降级。

### Phase 4 · 栏目级自由度

允许栏目声明自己的场景构造器、局部材质和文章排布，但继续受统一 URL、性能与导航契约约束。

### Phase 5 · 是否成为主入口的闸门

只有满足以下条件才考虑提升为空间主页：

- 中端移动设备稳定达到目标帧率；
- 搜索、键盘和屏幕阅读器流程完整；
- 首次访问者能在短时间内找到文章；
- 关闭动画或 WebGL 后功能等价；
- 构建、内容发布和常规文章维护没有显著复杂化。

## 8. 主要风险

| 风险 | 控制方式 |
|---|---|
| 空间效果喧宾夺主 | 阅读态冻结镜头，粒子降速降对比；默认内容优先 |
| 用户迷失方向 | 中心锚点、罗盘、返回平面版、浏览器历史一致 |
| 晕动与无障碍问题 | 减弱动态模式、短路径镜头、键盘树、DOM 语义层 |
| 移动端性能不足 | 自适应粒子密度、culling、低功耗模式、列表降级 |
| 两套 UI 难维护 | 单一内容源和 URL；空间层只消费构建清单 |
| Pixi 伪 3D 达到上限 | 将三维镜头交给 Three/WebGPU，Pixi 保留二维合成职责 |

## 9. 决策建议

这个方向值得做，但最有价值的创新不是“把网页塞进 Canvas”，而是让**个人知识结构拥有可探索的空间关系，同时保留网页作为文档的全部优势**。建议下一步只做 Phase 0 的独立实验，不修改生产首页；用真实栏目与真实文章数据验证它是否既有趣又可用，再决定是否继续。
