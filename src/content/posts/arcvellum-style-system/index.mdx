文风经常被简化成几个形容词，例如“克制、细腻、电影感”。这类标签很难指导实际写作，也无法判断一次生成是否真正符合目标。ArcVellum 将文风视为项目资产：它有语料来源、理论维度、生成约束、适用范围、反例、评测和版本身份。

## 文风工程的输入与输出

输入可以是作家作品、用户自有文本、授权语料或项目内部已经形成的稳定正文。每份语料作为独立子项目登记来源、语言、体裁、时期、长度和使用边界。

输出是一份可挂载 `StyleProfile`。它面向模型执行，主体长度按汉字统计控制在 500 至 2500 字。这个范围足以写清节奏、句法、视角、细节与禁忌，又能避免每场正文重复输入一本风格论文。

Profile 之外可以保存分析证据和测试报告，它们不必全部进入生成上下文。

## 分析维度

### 叙述声音

叙述者与人物的距离，评价与留白的使用，第一与第三人称的组织方式，自由间接引语以及叙述者对读者的默认关系。

### 句法与段落

长短句比例、句内层级、逗号与句号的分工、段落长度、换行节奏、对话嵌入、重复与转折的功能和密度。

### 叙事时间

场景、概述、停顿、跳切和省略怎样分配；过场如何交代；高潮通过动作、选择、信息或感官细节展开；回忆怎样进入当前时刻。

### 细节选择

哪些物件、动作、空间和身体细节经常被选择，它们是否承担关系、阶层、历史或情绪证据，哪些华丽表达会削弱准确性。

### 对话与人物

台词长度、言外之意和信息不对称，角色语言怎样体现身份又保持个体差异，内心解释与外部动作的比例。

### 意象与修辞

高频意象家族、比喻来源、抽象程度、重复修辞的有效条件，以及应避免的通用 AI 意象和空泛占位。

## 从观察到执行约束

风格分析不能停留在“该作者善用留白”。Profile 需要把观察翻译为动作：

```text
观察：人物情绪很少被直接命名
执行：优先写能改变关系的动作、选择或省略
反例：高潮处连续列举身体反应和抽象情绪
检查：删去情绪词后，读者能否从事实判断人物处境
```

每项约束应回答何时适用、怎样执行、怎样判断失效、允许什么例外。优秀 Prompt 提供正例和反例，且解释差异来自什么叙事功能。

## 降低模型惯性

默认风格提供一套朴素、流畅、准确的基线。它抑制常见模型惯性：

- 机械二分对照与连续转折；
- 器官轮班式情绪描写；
- “有什么东西”一类抽象占位；
- 冰、水、弦、悬崖等通用比喻；
- 景物恰好同步人物情绪；
- 短句三连和总结式金句；
- 菜名、物件和形容词的无功能列举；
- 用破折号代替结构清晰的句法。

这些规则进入生成约束，也进入 Lint 与 Review。部分软规则允许配置极低比例例外，用于确有功能的修辞；硬规则和项目自定义禁令保持严格。

## 标点策略

标点并非简单的频率优化。句号过多会把叙述切成机械碎片，逗号过多会把不同动作和认知黏在一起，破折号密集可能形成强烈风格，也可能掩盖逻辑。

Profile 需要规定中文引号形式、句群组织、逗号与句号的分工、分号的适用条件、破折号密度、冒号与括号的使用。确定性 Lint 负责统一形式和统计阈值，语义审查判断具体标点是否服务叙述。

## 隔离评测

文风 Profile 需要在未参与抽象的评测 Agent 上测试，避免同一上下文形成自证。

### 回译测试

将原文译为另一种语言，再让隔离 Agent 仅根据译文、内容约束和 Profile 译回中文。比较语序、叙述距离、节奏、意象选择和句法分布。目标是检验风格提示是否提供了足够执行信息。

### 大纲重建测试

把原文压缩为纯事件大纲，再用 Profile 扩展到接近原文字数。评测内容选择、场景展开、对话、叙述时间和语言纹理。这个测试更接近真实创作。

### 盲评与消融

让评审比较无 Profile、简短标签和完整 Profile 三组输出，并逐项移除某类约束，观察哪些内容真正影响生成。无增益条目应从运行时 Prompt 移到参考资料。

## 版本化与挂载

StyleProfile 拥有 id、version、source digest、适用体裁、语言、生成约束和评测摘要。作品可以挂载一个主风格和少量局部修饰；主风格拥有最高创作优先级，局部要求不能破坏人物、Canon 和可读性。

正文任务记录实际挂载版本。风格文件更新后，已生成候选不会被静默视为使用了新版本；需要重新生成或重新审查。

## 生成优先于事后纠正

风格系统首先进入 `compose-scene` 和正文生成 Prompt，包括节奏、句法、细节、标点、禁用惯性和当前场景适用条目。Review 再检查执行效果。

如果风格只在审查阶段出现，系统会反复让 Agent 清理已经形成的句法惯性。生成前约束能减少修订量，也能避免自动清理脚本误伤有效语义。

## 前端工作台

文风工作台把文件上传、文本粘贴、语料清单、抽象任务、测试报告、Profile 编辑和作品挂载放在同一页面。用户需要看见语料、版本、汉字数、评测结论、挂载作品和下一场正文收到的核心约束。

用户修改具有明确优先级，但修改后仍需重新验证 Schema 与挂载身份，防止界面保存了文本，运行时继续使用旧版本。

## 权利与适用范围

系统记录语料来源和用户声明，用于项目审计与团队协作。公开发布、商业使用和作家模仿涉及的权利由使用者依据当地法律、授权范围与发布场景判断。技术系统可以保留证据和边界，无法替用户取得素材权利。

## 一份可用 Profile 的验收

| 维度 | 验收问题 |
|---|---|
| 详细度 | 主体是否达到 500 至 2500 个汉字 |
| 可执行性 | 每项观察是否已转成生成动作和检查问题 |
| 具体性 | 是否包含正例、反例、密度与适用条件 |
| 可追溯 | 是否关联语料来源、摘要与版本 |
| 有效性 | 隔离回译、大纲重建或盲评是否显示增益 |
| 可挂载 | 正文任务是否记录准确的 StyleProfile 版本 |
| 可维护 | 更新后能否识别受影响候选并触发复核 |

文风工程的目标是让模型获得一套细致的语言行动准则。它既不能被压缩成几个标签，也不应膨胀成每轮都重复发送的文学史讲义。
