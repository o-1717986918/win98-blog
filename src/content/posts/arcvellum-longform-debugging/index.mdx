## 为什么要拿一个真项目来伤害工作流

在演示项目中，每个场景都可以恰好有足够资料，Agent 恰好一次交付正确文件，审查恰好不需要修订。这种数据可以证明 UI 能显示状态，却无法证明状态机能承受真实创作。

v0.99.0 的正式闭环选择了一个真实项目，走完 2 章、6 场景和 30,080 个中文内容字符。这个数字的意义不是大，而是足够让上下文累积、人物状态改变、字数预算消耗和审查修订开始真正影响后续场景。

## 8 月 21 日的提交历史像一张故障心电图

那一天的 commit 密度很高，主题却高度一致：长篇审查与修复生命周期。有的修复处理审查后的修订应该继承哪份证据；有的修复处理任务重开后的所有权；还有的防止章节晋升在个别场景尚未完成时越过门禁。

这些问题都不会在一段漂亮的生成文本里显现。它们只在第二次修改、第三次重试、章节跨越场景边界时出现。所以真项目不只是验收内容质量，更是验收每个过渡能否在重入后保持同一语义。

## 审查不能只是一份建议文本

正式路线中，候选稿和审查必须与内容指纹绑定。如果 Agent 在审查之后修改了正文，旧审查不能继续为新稿背书。反过来，修复若只是格式规范化，系统也不应无条件抹掉已有的人工选择。

为此，修订不是在原文件上无痕覆盖。它产生新候选，记录修复原因，再进入可检查的门禁。“最终看起来对了”不能回答“它怎样变对的”。

## 字数预算不是写作的速度表

长篇系统很容用累计字数制造进度感。ArcVellum 的闭环更关心 scene inventory 是否支撑该章目标，每个场景的字数是否有来自冲突、行动和状态变化的真实库存。

这一点也引出了多次预算修复：章节不应因为一个场景变长而自动判定完成；任务也不应通过反复描述来消耗预算。预算是诊断信号，不是要求 Agent 把句子吹大的 KPI。

## 闭环结果是一组证据，不是一个 DOCX

v0.99.0 对 scene、longform、review 和 export 四条路线分别执行 252、14、8、21 项检查，所有正式门禁达到零 blocker、零 warning、零 todo。Python 测试记录 1,274 项通过（一项跳过），Vue 有 60 个文件、186 项断言，Pi Worker 有 75 项测试。

这些数字不证明每个题材、每家模型供应商和每种审美目标都已成熟。它们只证明这一次正式闭环已经能从项目输入走到干净交付，且每步都留下可复查状态。对一个 Beta，这是“已经可以开始被认真使用”的证据，不是“已经没有问题”的声明。

## 失败不是一类状态，而是发生在不同边界

回看调试痕迹，失败至少分成五组。输入失败发生在项目资料、场景清单或 required reading 不完整时；签发失败发生在任务包与当前 revision 不一致时；生成失败包括 Agent 超时、工作区缺文件和输出路径偏离；审查失败对应连续性、角色状态、Canon 或形式约束未通过；晋升失败则发生在候选内容虽存在、证据却不足以进入正式区时。

把它们都压成 `failed` 会让恢复策略失真。输入缺口应回到预检，租约中断应重开任务，正文问题应生成带指纹的新修订，晋升门禁失败则必须保留正式状态不变。长篇闭环之所以需要几十次修复，不是因为系统“经常崩”，而是因为每个边界第一次面对重入时都暴露了自己的状态所有权。

## 场景完成与章节晋升之间还有一道聚合门

六个场景不是六次独立调用。某一场景结束后，人物位置、公开信息、未兑现承诺与字数库存会影响下一场；章节完成还要求该章的场景库存、审查状态和交付证据整体一致。单场结果若直接修改章节正式状态，后续修订便可能让章节显示“完成”，内部却含有失效候选。

因此场景级晋升只提交自己拥有的状态，章节级流程重新读取全部正式场景并计算聚合条件。这个看似重复的读取，是为了避免把前一步的乐观结论当成权威。真实开发里，多次“个别场景已经完成但章节不能晋升”的修复，正是这条边界逐渐变清楚的过程。

## 调试日志必须能回答“哪份正文被审过”

每次候选写入都产生内容摘要，审查记录引用摘要与任务身份，修复又产生新的摘要。恢复时若发现正文与审查指纹不同，系统宁可要求重审，也不把旧结论迁移到新内容。这增加了运行次数，却使最终交付可以沿证据链回到具体候选，而不是只相信最后一个文件名。

博客里的这篇调试日记也遵守同一原则：它没有把 commit 密度包装成开发效率，而是按输入、签发、候选、审查、晋升和交付重新整理故障。只有把失败放回所属模块，下一篇架构文章才知道应该改合同、adapter 还是测试，而不是继续向一个巨型 workflow 函数加条件。
