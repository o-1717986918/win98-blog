在一个长篇项目里，最糟糕的状态不是文件不存在，而是下游相信了一个并未正式完成的上游。一个 Agent 写出场景正文，另一个 Agent看到文件名便开始审查；审查 JSON 写完后，导出器又把它当作 clean pass。每一步都“有文件”，整条证据链却可能从未成立。

Workflow State Machine 的工作就是拒绝这种乐观推断。

## 一项正式任务的最小闭环

注册路线遵循固定循环：

```text
task-next -> task-open -> 平台 Agent 写预期产物
-> task-submit -> task-complete -> workflow-state / workflow-validate
```

`task-open` 不只是展示说明，它签发 Task Package；`task-submit` 记录产物与 task id；`task-complete` 只有在预期文件被检查后才能写 completion marker。一个文件可以存在，但 submission 缺失、completion 仍 pending，或 upstream gate 仍 blocked。

## 为什么要有这么多账本

| 账本 | 它证明什么 |
|---|---|
| `route_state.json` | 当前路线的派生状态 |
| `*.task.json` | 哪一项任务被正式签发 |
| `*.submission.json` | 平台 Agent 提交了哪些产物 |
| `*.agent_completion.json` | 预期产物已经被检查 |
| `task_events.jsonl` | issued / opened / submitted / blocked / completed 的追加事件 |
| `workflow_contract.*` | 状态、事件、任务、产物与上下游关系是否一致 |

它们看似重复，实际上分别覆盖意图、提交、核验与历史。`workflow-validate` 可以发现下游已经 pass、上游仍 blocking，或 submission 引用不存在的 task；`workflow-dashboard` 聚合路线审计、待办 sidecar 与最近事件，但它是只读投影，不能因为仪表盘显示绿色就推进项目。

## Review CI 不是一个评分器

审查维度包括 Canon 一致性、人物 OOC、场景目标、空草稿、blocked 场景、人工确认、Agent Review JSON Schema 与挂载文风遵循。结论有 `pass`、`pass_with_notes`、`revise_required` 和 `reject`。

这里最容易被误解的是 `pass_with_notes`。它不是“差不多可以”，而是没有阻断级问题、但仍有必须局部处理的 notes。revision actions、warnings、style notes 必须具体可执行；下一轮生成会把它们注入 review notes，写作 Agent 完成局部修订，再经过复审达到 clean pass。章节 ready、写回、导出和发布不能用 waiver 把 notes 静默吞掉。

## 状态机不替 Agent 做文学判断

CLI 决定下一项合法步骤、签发任务包、记录提交、验证确定性 Gate。平台 Agent 仍负责人物推演、分支比较、composition、正文、审查与修订。两者不是“机器规则对抗创意”，而是把创意判断与项目权力分开：Agent 能说“这段可以进入下一轮”，但不能直接把候选写成 Canon。

这种分工也解释了为什么不应在前端复制工作流。星仪或任务面板可以显示 lifecycle 和 action availability，真正动作仍要回到 application command 与 CLI route。否则 UI 会产生第二状态机，刷新或版本迁移后就可能与正式账本分叉。

## 长篇路线为什么还要增加读者门禁

字数预算与场景库存完成后，路线仍不止于“有足够多场景”。长篇规划依次经过预算 Agent 任务、预算审查、场景库存任务与审查、章节义务任务与审查。十万字以上或多卷项目还要求 Reader Experience Contract：逐场填写读者问题、承诺、兑现/延迟、张力来源与余味。

这不是用表格代替创作，而是阻止数量达标掩盖叙事空心。正式中文长度也按清理后的内容字符计算，排除路径、Markdown 架构、review notes、状态补丁与 Agent Task 区块；机器非空白字符只作诊断。

## 失败时怎样修，而不是跳过

当 route state 可疑时，维护者同时查看 `workflow-state`、`agent-task-status`、`route-audit` 和 `workflow-validate`。修复目标是恢复账本一致性，而不是直接改 `route_state.json` 为 pass。手工 workaround 只有在正式命令确实尝试并失败、且留下等价 provenance 时才可能进入审查，也不能绕过后续 Gate。

这种严格让批量并发变得可能。多个 Agent 可以同时完成不同候选任务，但统一 Task ID、submission、completion 与事件 Schema 让最终合并仍能核验上下游。没有这层状态纪律，“并行创作”只会更快地产生一批无法判断来源的文件。

## 真正的完成定义

ArcVellum 的完成不是“正文目录里多了一个 Markdown”，也不是“测试全部变绿”这么单一。它是一组一致事实：预期产物存在，来源可追踪，Schema 合法，审查 clean，状态写回受控，上游无阻断，下游没有抢跑，导出的正文只来自已晋升内容。

这也是阅读器为什么看起来比工作流简单。读者只需要一本干净的书；复杂账本的价值，恰恰是让这些内部工程痕迹不必混进那本书。
