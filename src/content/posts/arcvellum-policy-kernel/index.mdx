这个内核不是从一开始就完整的理论模型。长篇闭环调试里，几乎每个修复都在回答同一个问题：候选、审查、修订、晋升和写回之间，究竟谁有权说“这一版已经成为正式事实”？只要 UI、Runner 或 Agent 中有任何一个可以独立回答，状态就会分裂。

## 为什么权威必须只有一个

Agent 系统最危险的状态不是失败，而是多个部件都认为自己成功。前端按钮把任务标成完成，Runner 输出一段正文，某个脚本又直接改写 Canon；下一次运行时，系统无法判断哪一份状态应当被相信。

ArcVellum 将 CLI 状态机设为唯一权威：路线不是 UI 中的一串勾选框，而是一套由项目事实推导出来的合法状态。Studio 可以请求动作，Worker 可以执行任务，Agent 可以生成产物，但只有内核能判定提交是否满足当前路线的门禁，并签发下一项任务。

## 任务包是最小治理单元

正式任务包至少需要回答：这是什么任务、属于哪条路线、允许读取哪些资料、必须遵守哪些硬约束与风格约束、可写哪些输出、如何提交、如何完成，以及会被哪些 Gate 验证。

这比“给 Agent 一段系统提示词”强得多，因为权限与预期产物变成可检查的数据。任务包中的 Prompt 资产有身份，输入路径有白名单，输出有 Schema，完成命令也不能携带任意 shell 语法。创作内容仍然开放，但工作边界不依赖模型自觉。

| 层次 | 典型对象 | 是否可直接成为正式事实 |
|---|---|---|
| 推演 | 角色反应、世界后果 | 否 |
| 候选 | 分支、正文草稿、Canon 提案 | 否 |
| 审查 | AgentReview、Style Lint、连续性证据 | 否 |
| 晋升 | 指纹匹配且门禁通过的正文 | 是 |
| 写回 | 人物状态、Canon 分类、连续性账本 | 由正式操作完成 |

## 候选与事实必须分层

长篇创作中，模型经常为了探索而提出互相矛盾的可能性。允许它发散并没有问题；问题是把发散过程和正式世界状态放进同一个文件。ArcVellum 通过候选层吸收不确定性，再由分支选择、审查和晋升把单一决定写入正式层。

内容指纹解决了另一个隐蔽问题：审查 A 版本、发布 B 版本。候选稿、Review、修订与晋升之间需要可核对的内容身份。否则一份“通过”记录只能证明某段旧文字曾经被看过。

## 硬门禁与文学判断如何共存

确定性 Gate 适合检查 Schema、路径、字数范围、引用来源、内容指纹和禁止模式；语义审查适合判断人物动机、场景功能、读者效果与文风。把所有问题交给 LLM 会造成不可重复，把所有问题写成正则又会扼杀创作。

ArcVellum 的办法是让两者串联：AgentReview 提供语义判断，Lint 和预检验证机器事实，正式晋升同时要求证据链完整。策略可以调整推演深度、分支数量、叙事距离、目标字数和修订方式，但不能删除系统注入的底线门禁。

## 内核目前仍有何技术债

正式内核审查没有把成熟描述成完美。现有输出仍有较多人类可读的 `key: value` 文本，尚未全部升级为版本化 JSON；任务命令仍是受严格语法约束的 shell-like 字符串，而不是结构化 argv；任务 Schema 还应显式声明 `execution_policy`、`human_gate`、`agent_role` 与 Runtime 能力；预期输出也仍混合确定性产物、Agent 产物与完成产物。

这些债务的共同方向是：把隐含约定变成版本化合同。它们不会否定当前状态机，却决定系统未来能否在更多 Runtime、更多版本和更复杂恢复场景下保持可解释。

## 为什么嵌入快照而不是运行时依赖 Skill

Studio 内置 `literary_engineering_studio_engine`，并明确不在运行时发现另一份 Skill 仓库、不依赖环境变量路径、不用 Git submodule。未来同步需要记录来源版本，逐项比较任务注册、Schema、Prompt 资产、导出行为和测试，再选择性合并。

这牺牲了“自动得到上游最新代码”的便利，却换来可安装产品最重要的属性：同一个安装包中的规则不会因用户机器上另一个仓库变化而漂移。文学工程内核首先是发布物中的政策快照，然后才是可以演进的代码。

## 内核的真正产品价值

当模型越来越强，生成一段文字的差异会缩小；而状态治理、证据链、失败恢复与正式交付的差异会扩大。CLI 唯一权威并不性感，但它让 ArcVellum 能够回答“这段文字为什么在这里、经过了什么、改变了哪些正式事实、还能否重跑”这些长篇项目迟早要面对的问题。
