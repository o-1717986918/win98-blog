我很长时间都只把 ArcVellum 称为“工作室”或“系统原型”。仓库里已经有状态机、星仪、Agent Runtime 和安装包，但这些都可以在演示数据上看起来成立。直到 v0.99.0 用真实项目走完 2 章、6 场景、30,080 个中文内容字符，而且所有正式路线门禁保持零 blocker、零 warning、零 todo，“产品”才不再只是愿望。

## 产品命题：不是让 AI 多写一点

单次生成解决的是段落问题，长篇创作解决的是状态问题。人物的 belief、desire、fear 会变化；世界规则有不可违反的边界；场景既承担局部冲突，也必须接续章节节奏、读者问题与全书字数预算。把这些信息全塞回一条越来越长的对话，只会让事实来源、候选设想和已经确认的正文彼此污染。

ArcVellum 的核心选择，是把作品理解为一个长期运行的工程项目。Canon、人物档案、场景状态、分支决策、审查证据、字数预算与交付物都有正式位置；模型可以生成候选，但不能仅凭一次回答就改写这些位置。

> “Agent 可以创作”与“Agent 拥有项目权力”不是同一件事。ArcVellum 的价值，恰恰来自对两者的拆分。

## 从场景到正文的正式路线

仓库把一个场景的开发组织为稳定契约：规划与上下文准备之后，先进行角色推演和分支比较，再形成编剧态约束，随后才生成正文候选。候选还要经过独立审查、确定性 Lint、必要修订与内容指纹核对，才能晋升为正式正文。晋升之后，人物状态、Canon 候选和连续性账本才被允许写回。

这条链路看似比“输入提示词—得到正文”更慢，却把最昂贵的失败显式化了：

- 审查的版本与最后发布的版本是否一致；
- 人物变化是否有前因，而不是模型临场补写；
- 字数增长是否来自足够的剧情库存，而非句子膨胀；
- 读者被承诺的问题是否被暂扣、推进或兑现；
- 输出失败后，系统能否知道失败发生在哪个步骤。

## 三个面向同一状态的产品表面

叙事星仪把章节、场景、人物联系、候选分支、审查债务和当前任务投影为空间关系；正文阅读器只收录已经晋升的内容；悬浮顾问则从只读项目投影回答问题，并且只能提出白名单动作。三者不是各自维护一套“看起来合理”的数据，而是从同一份受内核验证的项目状态取得读模型。

这种设计避免了 Agent 产品常见的错位：聊天区声称任务完成，文件系统却没有结果；进度条走到 100%，门禁仍然缺证据；界面展示了漂亮的节点图，实际项目中并不存在这些关系。

## v0.99.x 到底证明了什么

v0.99.0 的发布记录给出了比功能列表更有价值的证据：它通过与产品前端相同的公开 Studio API 创建干净项目，使用内置 Pi Worker 和真实模型连接，以 `full_auto` 路线完成两章六场、30,080 个中文内容字符的作品。六个场景均走过推演、分支、生成、独立审查、晋升、状态和 Canon 写回；四条正式路线合计检查 295 项 Gate，最后为零阻断。

这证明了“完整路径可以闭环”，也证明了正式正文与工程痕迹能够在交付时分离。但它没有证明：所有题材都能长期维持文学质量、所有模型供应商在相同预算下表现一致，或无人值守运行在弱网和配额波动下永远可恢复。仓库把产品标为 Beta 是准确的。

v0.99.1 又解决了另一类问题：全自动授权不再被人为的任务数与时长上限中断，同时保留用户暂停、Provider 配额、确定性 Gate 失败、无进展与恢复耗尽等停止条件。它移除的是授权天花板，不是质量门禁。

## 适合谁，不适合谁

ArcVellum 适合把连续性、人物后果、文风约束和长期可追溯性看得比“一次生成速度”更重要的小说、剧本与伪记录作品创作者。它也适合研究 Agent 工作流的人：项目把任务包、权限、预检、状态晋升和 UI 投影放在同一条真实产品路径中。

如果目标只是润色一段文字、快速发散十个点子或完成短篇一次性生成，完整状态机的成本可能没有必要。文学工程不是所有写作的默认答案；它是作品规模、协作复杂度和持续时间达到一定阈值后的基础设施。

## 安装与现实边界

Windows 发行包包含 Tauri 桌面端、本地应用服务、文学工程内核、Pi Worker 与 OpenCode Runner，不要求用户预装 Python、Node 或 Rust。模型连接与推理费用仍由用户选择的服务或本地端点负责，凭证不进入项目文件、任务包和普通日志。

当前正确的期待是：ArcVellum 已经是一条可安装、可更新、可审计的 Beta 产品线，而不是只有概念图的原型；同时，它仍需要更多真实长篇样本、干净系统安装矩阵、供应商故障测试与长期文学质量评估，才能把一次严肃闭环变成统计意义上的可靠性。
