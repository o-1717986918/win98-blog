星仪的开发史不是一张设计稿变成代码的直线。仓库里保留了 typographic celestial field 评审：哪些原型的空间连续性和排版化天体值得借鉴，哪些重复 WebGL renderer、后期特效和距离隐藏必须拒绝。最终方案明确要求“借思想，不借源码”，而且每个节点都必须来自真实 projection，不用 demo data 填场。

## 叙事星仪不是“知识图谱皮肤”

长篇项目的数据天然是异质的：章节与场景有时间顺序，人物关系构成网络，审查债务和字数预算是强度信号，当前任务又具有即时性。如果把它们压进同一张二维节点图，结果往往是每个节点都争夺注意力；如果退回表格，作者又很难形成作品整体正在向哪里生长的感受。

ArcVellum 将星仪定义为空间操作系统，而非站点背景。章节锚点形成主脉，场景在章节附近成簇，关系线只在语义相关时出现，当前任务与风险以仪器层叠加。工作台和全视口模式共享同一投影，但根据视野密度采用不同表达。

## 前端真正消费的是读模型

Vue 客户端不应从零拼装文学真相。应用服务把内核状态整理成版本化投影，经 API 与 SSE 交付；前端 Feature 只负责把这些投影解释为可操作表面。这样做有三个收益：

1. 刷新、断线重连和桌面重启后，界面能从持久化事件和 revision 恢复，而不是依赖内存中的动画状态。
2. 星仪、正文阅读器与任务工作台可以共享“哪一份内容已经晋升”的语义。
3. 投影结构改变时，可以先变更合同，再分批迁移 API adapter 和前端消费方。

仓库的模块化审计将 Feature client、跨 Feature 的 composition registry 与具体页面装配分开，目的不是追求目录洁癖，而是防止星仪为了调用任务面板而直接拥有另一个 Feature 的实现。

## “主脉 / 全部”是一项信息设计决策

v0.99.1 只保留 Moss / Mineral 品牌视觉，并增加“主脉 / 全部”信息密度。主脉模式优先章节、当前场景、主要人物与正在影响创作的证据；全部模式才展示完整工程事实。

这比提供五套主题更重要。复杂系统的可用性很少由颜色数量决定，更多取决于默认视野是否正确。作者第一次打开项目时，需要先看见叙事主轴和当前位置，而不是同时处理每条关系、每份档案和每个审查标记。

视觉层级也必须可验证：章节字号、节点点击范围、关系线对比度、被选中对象与仪器窗口的关联都应有视觉回归，而不能靠设计师“感觉差不多”。仓库的 Playwright 验收覆盖 100、300、1000 场景规模，说明它至少把规模当成了正式测试维度。

## 仪器窗为何可以拖动、多开、折叠

推进、决策、规则、节奏、项目健康度和正文不是固定导航页面，而是作者围绕当前问题临时组合的观察工具。允许多开与拖动，是把“页面切换”改成“工作面布置”：比较分支时可以同时保留人物状态；检查节奏时可以让章节脉络仍在背景中可见。

这套自由度需要约束。窗口位置应可恢复，关键动作不能因为窗口被盖住而丢失，移动端不能照搬桌面多窗模型。真正的产品自由度来自稳定的状态与焦点管理，而不是简单给每个面板加 `position: absolute`。

## 正文阅读器是星仪的反面

星仪负责高密度观察，阅读器负责低干扰沉浸。正文阅读器只呈现已经通过正式门禁的场景，并支持连续/分章模式、全文搜索、目录、书签、阅读位置恢复、字号、行距和日夜主题。创作继续推进时，新正文只做温和提示，不把读者强行带离当前位置。

这里的关键不是功能数量，而是数据边界：候选稿、审查意见和内部场景编号不能泄露进“作品正在成为一本书”的体验。读模型先过滤事实，排版才有意义。

## 性能债务必须被写进设计文档

v0.99.1 的模块化审计明确保留了两个前端债务：1000 场景投影 API 约 0.37 秒，但浏览器完整首帧约 30–45 秒；星仪仍有一个较大的 bundle chunk。前者指向布局与渲染，后者指向 Feature 内的懒加载，而不是文学内核。

这份诚实很重要。节点图最容易用“少画一点”掩盖性能问题，但那会改变产品语义。更可靠的方向是分层加载、视口裁剪、空间索引、离屏缓存与渐进式标签，保持数据完整，同时让首帧只承担当前视野必需的工作。

## 可复用的设计结论

ArcVellum 的前端思想可以概括为四句：先建立唯一事实投影，再设计空间隐喻；默认视野必须有主次；高密度操作面与低密度阅读面应该分离；规模问题属于渲染层，就在渲染层解决。这样，视觉辨识度才不是一次性的主题包装，而是架构产生的结果。
